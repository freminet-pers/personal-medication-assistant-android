# 个人用药助手：第三轮界面、动画与交互优化计划

> 本文是直接交给开发 AI 执行的任务书。本轮目标不是重写产品，也不是只做一套静态效果图，而是在现有 Android 工程上完成一个可安装、可升级、数据不丢失的 `0.2.0` 版本。

## 一、本轮交付目标

在不破坏现有用药记录、药品库存、健康档案、资料文件、提醒和 DeepSeek 功能的前提下，完成以下工作：

1. 系统性改善界面层级、排版、颜色、间距、图标与空状态，使应用看起来像一款可信、安静、长期可使用的个人健康工具。
2. 加入克制、连贯、不会妨碍操作的界面动画与状态过渡。
3. 修正应用内不符合普通用户习惯的交互逻辑，尤其是直接暴露内部枚举、星期位掩码、技术状态码、仅靠 Toast 报错等问题。
4. 保持原包名和原签名身份，提升版本号，验证旧版可以覆盖安装且本地数据继续可用。
5. 构建、测试并交付带版本号文件名的 APK，以及简洁、可核验的验收报告。

## 二、版本与升级规则（强制）

本轮版本固定为：

- `versionCode = 2`
- `versionName = "0.2.0"`
- 应用显示名称仍为“个人用药助手”

注意：用户所说的“每次重新签名一个版本号”，实际要求是每次交付提升版本号，不是更换签名。

必须遵守：

1. 不改变 `applicationId`、包名、签名证书或现有签名配置；否则无法正常覆盖安装或会造成数据割裂。
2. 每个可交付版本的 `versionCode` 必须严格大于上一版。本轮从 1 提升到 2。
3. 功能迭代默认提升次版本号，故本轮为 `0.2.0`；小范围修复才提升补丁号。
4. “关于”页面必须从构建信息动态读取并显示版本名和版本号，禁止手工写死后忘记更新。
5. 最终 APK 另复制或重命名为清晰的版本化文件，例如 `个人用药助手-v0.2.0-debug.apk`；保留 Gradle 默认产物也可以。
6. 交付前用 APK 分析工具、`aapt dump badging` 或等价方式核对实际 APK 内的包名、`versionCode`、`versionName`，不能只检查源码。
7. 尽可能执行从 `0.1.0` 到 `0.2.0` 的覆盖安装测试，确认数据库、Keystore 中的设置及本地文件均未丢失。若缺少真实设备或 ADB，必须在报告中明确列为未完成的外部验证，不能声称已经验证。

以后每轮迭代也要重复这套规则，并在开始开发前先确认当前 APK 和 Gradle 中的最高版本号，避免回退或重复。

## 三、视觉方向

视觉主题定为“安静的个人健康日志”，兼顾医疗信息的可信感与日常生活工具的亲和感。

### 3.1 设计语言

- 主背景使用温和的米白或极浅灰，而非刺眼纯白。
- 主色使用低饱和玉绿色、青绿色或深松石色，代表完成、健康和稳定。
- 琥珀色用于临期、待处理和温和警示；红色只用于过期、危险或破坏性操作。
- 卡片通过少量色差、描边和克制阴影形成层级，不堆叠大面积渐变和发光效果。
- 圆角、间距、字号、图标大小统一使用设计 token，避免每个页面各自随意设置。
- 中文排版优先保证清晰：药名、剂量、时间是第一视觉层级，辅助信息适当弱化。
- 避免紫蓝渐变、“AI 炫光”、到处都是大胶囊按钮和模板化 AI 卡片；AI 是能力，不是整款应用的视觉主题。

### 3.2 页面共同结构

- 顶部应用栏显示当前页面标题与必要操作，不要在每个页面反复占据大面积展示产品名。
- 所有页面正确避让状态栏、显示刘海和底部手势区域。
- 底部导航保留最多五项：今日、药物、资料、健康、更多；加入语义明确的图标和文字。
- 当前导航项使用清晰但克制的选中底色或指示器；切换后选中状态必须同步。
- 页面主要按钮的位置、圆角、颜色和按压反馈保持一致。
- 使用真实图标资源或 Material 图标，避免用表情符号充当正式功能图标。

## 四、主要页面优化

### 4.1 今日

- 顶部呈现“下一次用药”主卡：药名、剂量、时间、距离现在多久、确认服用按钮。
- 加入当日完成进度，但不要喧宾夺主；可以使用进度条或小型环形进度。
- 用药任务按清晨、上午、中午、下午、晚间或具体时间形成时间线，避免所有卡片同权重平铺。
- 已完成任务降低视觉权重但仍可查看；允许撤销刚刚的完成操作。
- 无任务时显示友好的空状态和“添加用药计划”入口。
- 漏服、跳过、稍后提醒等状态使用清楚的人类语言，并明确是否会影响后续提醒。

### 4.2 药物

- 增加药名搜索以及“正在服用、库存药、临期、已停用”等筛选入口。
- 药物卡片优先展示药名、规格、当前服用状态、库存与最近过期时间。
- 删除、停用、编辑等低频操作收进更多菜单，避免每张卡堆满按钮。
- 临期和过期状态必须有文字与颜色双重提示，不能仅靠颜色区分。
- 添加药物流程保留拍照/上传给 DeepSeek 识别，但要提供手工录入和稍后补充资料的明确入口。

### 4.3 资料与识别

- 将药盒、说明书、病历等资料按类型组织，并显示缩略图、名称、录入时间和识别状态。
- DeepSeek 识别过程明确区分：待上传、正在上传、正在分析、等待用户核对、已保存、失败。
- 不显示伪造的百分比进度；无法获知真实百分比时只显示阶段和活动指示器。
- 识别结果必须进入“核对后保存”，突出 AI 可能识别错误，不可静默覆盖既有数据。
- 支持查看原图/原 PDF、查看结构化结果、修改后保存、重新识别和删除。
- 失败页面说明可理解的原因并提供重试；网络错误不能让用户误以为资料已经丢失。

### 4.4 健康档案

- 按基础信息、过敏史、既往病史、用药禁忌、检查/病历摘要等类别呈现。
- 首页只显示摘要和最近更新，点击进入编辑详情，避免一个超长表单铺到底。
- 明确说明哪些信息会提供给 AI 作为上下文，并允许用户查看、修改、删除。
- 空字段不应显示大量“无”，使用简洁空状态与补充入口。

### 4.5 更多、设置与 AI 助手

- “更多”按 AI 与资料、提醒、隐私与数据、外观、关于进行分组。
- 助手和设置从“更多”进入后，返回键应回到“更多”，不能直接退出应用或跳错页面。
- API Key 的保存、测试、删除状态清楚分开；保存成功不等于网络测试成功。
- 网络请求期间按钮显示加载状态并防止重复提交，同时允许在合理情况下取消或返回。
- 关于页面显示应用名、`versionName`、`versionCode` 和必要的隐私/医疗免责声明。
- 若保留本地对话记录，必须支持单条或全部删除，并明确数据只保存在本机；不要未经用户确认上传整个历史。

## 五、必须修正的应用内逻辑

1. 禁止直接向用户暴露 `DAILY`、`WEEKLY`、`INTERVAL`、`PRN`、`TEMP`、`IN_STOCK` 等内部枚举值。界面分别显示“每日、每周、每隔一段时间、按需服用、临时用药、库存中”等中文；数据库和接口层仍可保留内部值。
2. 星期选择使用“周一至周日”可点选标签，不让用户手工填写位掩码或数字代码。
3. 日期、时间、周期、剂量单位和药品状态使用选择器、单选项或可理解的控件，减少自由输入造成的格式错误。
4. 较长的添加/编辑流程拆成有明确标题的小步骤，或使用可滚动分区；键盘弹出时当前输入项与主要按钮不得被遮住。
5. 必填、格式错误和逻辑冲突在对应输入项旁显示，不能只弹出短暂 Toast。
6. 保存操作有明确成功反馈；普通反馈优先使用 Snackbar 或行内状态，避免 Toast 连续轰炸。
7. 离开未保存表单时提示保留、放弃或继续编辑；屏幕旋转和系统重建后尽量恢复草稿。
8. 所有空页面提供下一步入口；所有失败状态提供重试或替代路径。
9. 列表刷新、删除、完成服药后保持当前页面和滚动位置，避免整个应用突然跳回首页。
10. 删除药物、资料或健康记录前显示对象名称与后果；可撤销的操作优先提供短时撤销。
11. 识别生成的药物资料与用户手工修改内容要区分来源；重新识别不能无提示覆盖用户修订。
12. 不得因为 UI 优化而改变提醒调度、药物相互作用提示、过期提醒和本地隐私边界的既有含义。

## 六、动画与过渡规范

动画必须帮助用户理解“从哪里来、去了哪里、状态发生了什么变化”，不能只为炫技。

### 6.1 基础参数

- 普通按压和小状态变化：约 120–180 ms。
- 卡片展开、页面内容切换：约 180–300 ms。
- 常规交互动画原则上不得超过 400 ms。
- 使用统一缓动曲线和统一 motion token，不在各页面散落魔法数字。
- 动画不得阻塞点击、请求、导航，也不得依赖动画结束才保存关键数据。

### 6.2 推荐动效

- 底部导航：选中指示器平滑移动，图标/文字仅做轻微颜色和缩放变化。
- 页面切换：轻微淡入配合极小位移，避免整页大幅横飞。
- 卡片首次载入：可做一次轻量错峰进入，间隔约 20–40 ms；列表每次刷新不要重复表演。
- 按钮和卡片：保留 Android ripple，并加入非常轻微的按压缩放，松手立即恢复。
- 完成服药：勾选状态、颜色和进度自然过渡；条目如需移动或折叠必须让用户看清去向，并提供撤销 Snackbar。
- 新增或删除列表项：使用高度与透明度过渡，避免瞬间跳动。
- 进度条、库存和当日完成率：数值变化时平滑过渡，不反复闪烁。
- 对话框或底部面板：与触发控件保持空间关系，进入退出速度一致。
- AI 识别：使用低干扰的阶段切换和活动指示器；只在真正处理时循环，结束或失败立即停止。

### 6.3 可访问性与性能

- 遵守系统动画缩放和“减少动态效果”意图；当动画比例为 0 时，装饰性动画应关闭且功能仍完整。
- 不用动画作为唯一的信息载体，同时保留文字、图标或状态说明。
- 大字号、屏幕阅读器、触控目标和颜色对比度必须可用。
- 避免在长列表中同时启动大量阴影、模糊和无限动画；中低端设备上滚动应保持流畅。
- 不为本轮动效贸然迁移到 Compose。优先在当前 View 架构中稳妥实现。

## 七、代码组织与实施顺序

当前 `MainActivity` 承担过多页面创建和交互逻辑。本轮允许进行“服务于稳定迭代的适度拆分”，但禁止把任务扩大成全量架构重写。

建议顺序：

1. 先盘点现有页面、状态、数据入口和回退路径，记录不可破坏的功能。
2. 建立统一的颜色、字号、圆角、间距、控件样式与 motion token。
3. 把重复的卡片、空状态、加载状态、分区标题和表单控件抽成可复用组件或帮助类。
4. 必要时将页面渲染和交互从 `MainActivity` 拆到小型 controller/view/helper；数据库、提醒和网络层无必要不重写。
5. 先完成通用壳层、系统栏与底部导航，再依次优化今日、药物、资料、健康、更多。
6. 最后加入动画，避免动画掩盖尚未修好的状态逻辑。
7. 每完成一个页面即做一次小范围手动验证，最后只做一次完整回归和最多两轮针对性修复，防止陷入无止境审查循环。

## 八、测试与验收

### 8.1 必测功能

- 新增、编辑、停用、删除药物与批次。
- 创建每日、每周、间隔、按需和临时计划；时间与星期选择正确。
- 完成、撤销、跳过、稍后提醒等今日任务操作。
- 过期与临期显示、提醒调度不回退。
- 药盒/说明书/病历的上传、DeepSeek 识别、核对、修改、保存、失败重试。
- API Key 保存、读取、删除与连接测试；密钥不得进入日志、报告、源码或 APK 资源。
- 健康档案的新增、编辑、删除及 AI 上下文使用边界。
- 返回导航、旋转/重建、键盘遮挡、加载中重复点击和网络失败。

### 8.2 视觉与设备矩阵

至少检查：

- 约 360dp 和 412dp 两种宽度。
- 浅色模式；若应用正式支持深色模式，也必须检查深色，否则不要仅做一半的伪深色主题。
- 默认字号和系统大字号。
- 手势导航和三键导航的安全区域。
- 无动画或动画比例为 0 时的核心操作。

### 8.3 构建与升级

- 运行现有单元测试及与本轮改动相关的新增测试。
- 完成一次 clean build 或等价的可复现构建。
- 检查 APK 实际版本信息、包名、签名一致性和 SHA-256。
- 有设备时执行旧版覆盖安装、启动、核心数据抽查和新版冷启动。
- 没有设备时不反复等待；完成能在本机完成的验证，并在报告中列出需要用户真机复核的最小清单。

## 九、明确不做

- 不更换应用名称、包名、签名身份或 DeepSeek 默认模型策略。
- 不重新引入本地 ML Kit OCR；现有 DeepSeek 图片/文档识别方向保持不变。
- 不进行无必要的 Compose 全量迁移、数据库重写或网络层重写。
- 不增加与本轮目标无关的大功能。
- 不以静态原型、截图或“建议清单”代替实际 APK 修改。
- 不进行数小时循环审查。验证发现问题后最多集中进行两轮修复；外部条件无法验证的内容如实记录。

## 十、交付物

完成后必须提供：

1. 已修改并可构建的完整 Android 工程。
2. `个人用药助手-v0.2.0-debug.apk`（若另有 release 包需清楚区分，不能混淆）。
3. APK 的 SHA-256、包名、实际 `versionCode`、实际 `versionName` 和签名核验结果。
4. `../validation/15_第三轮界面动画与交互验收报告.md`，内容包括：
   - 实际完成的页面与交互改动；
   - 动画清单及持续时间；
   - 应用内逻辑修正清单；
   - 测试命令与实际结果；
   - 覆盖安装和数据保留是否真实验证；
   - 未验证事项和真机最小复核步骤；
   - 最终 APK 的绝对路径和 SHA-256。
5. 如工程已有说明文档，同步更新安装方法和版本信息。

## 十一、完成标准

只有同时满足以下条件才可宣布完成：

- 界面优化、动画和交互逻辑已经落到工程代码中，而非仅写文档。
- 现有核心功能没有已知阻断性回归。
- APK 构建成功并可定位。
- APK 内实际版本为 `versionCode 2 / versionName 0.2.0`。
- 包名和签名身份未改变，可用于覆盖旧版。
- 验收报告区分“已自动验证”“已真机验证”“尚待用户真机验证”，没有夸大结论。
