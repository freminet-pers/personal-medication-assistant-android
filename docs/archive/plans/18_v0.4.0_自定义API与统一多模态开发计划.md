# 个人用药助手 v0.4.0：自定义 API、统一多模态与界面一致性开发计划

## 1. 本轮目标与交付边界

本轮不是只替换界面上的模型名称，而是把 v0.3.0 中写死的 DeepSeek 单供应商实现，重构为可配置、可测试、可迁移的 AI Provider 架构，同时修复助手页及 API 配置流程中与全应用风格不一致的问题。

最终必须同时做到：

1. DeepSeek 预设升级为 **DeepSeek V4.1 Flash**，展示名为“DeepSeek V4.1 Flash”，实际 API 模型 ID 使用官方当前值 `deepseek-flash`。
2. `deepseek-flash` 同时处理文字与图片，不再调用或展示独立的 `deepseek-v4-flash-vision-exp`。
3. DeepSeek 只是一个内置预设；用户可新增、编辑、切换和删除自定义 AI Provider。
4. 支持三种明确的请求协议：
   - OpenAI Chat Completions：`POST /chat/completions`
   - OpenAI Responses：`POST /responses`
   - Anthropic Messages：`POST /messages`
5. DeepSeek V4.1 Flash 可复用其 DeepSeek Key 使用官方原生搜索；其他模型只有在用户明确配置搜索 API 后才能开启联网搜索。
6. API 配置、图片识别、普通问答和搜索分别进行真实协议适配、错误映射与 Mock 合约测试，不能用“连接成功”代替功能测试。
7. 助手页、API 配置页、弹窗、表单、按钮和状态色必须复用全应用同一套 Design System，消除截图中突兀的紫色按钮、浅紫卡片和临时组件风格。
8. 版本升级为 `versionCode 4`、`versionName 0.4.0`，保持 `applicationId=com.lunamax.medassistant`、原签名兼容和旧数据库数据可迁移。
9. 完成自动化测试、模拟器验收、APK 交付、中英文文档、Git 提交、GitHub 推送和 `v0.4.0` Release。

本轮不承诺“任意厂商、任意私有协议都自动兼容”。只对本文列出的三种协议和可配置的兼容开关负责；厂商使用非标准字段时，应用应给出可理解的失败原因，而不是伪报成功。

## 4. Provider 数据模型与安全存储

### 4.1 Provider Profile

新增稳定的 Provider Profile，至少包含：

- 不可变 UUID。
- 显示名称。
- 类型：内置 DeepSeek / 自定义。
- 协议枚举：`OPENAI_CHAT_COMPLETIONS`、`OPENAI_RESPONSES`、`ANTHROPIC_MESSAGES`。
- base URL。
- 模型 ID。
- 输入能力：文字、图片。
- 推理能力与“快速 / 深入 / 最大”的线缆值映射。
- 认证方式：Bearer、`x-api-key`、二者同时、无鉴权。
- `anthropic-version`，默认 `2023-06-01`。
- 连接与读取超时。
- OpenAI 兼容差异项：system/developer role、`max_tokens` / `max_completion_tokens`、DeepSeek thinking 格式。
- 最近一次测试状态、时间、测试类型和脱敏错误码。
- 是否为当前默认 Provider。

内置 DeepSeek Profile 默认值：

- 显示名：DeepSeek V4.1 Flash
- 模型 ID：`deepseek-flash`
- 默认协议：OpenAI Chat Completions
- base URL：`https://api.deepseek.com`
- 文字：支持
- 图片：支持
- 推理档位：快速=`off`、深入=`high`、最大=`max`
- 内置项不允许删除；可测试、切换协议，或“复制为自定义”后再修改。

### 4.2 Search Profile

搜索配置与对话 Provider 解耦，支持：

1. **DeepSeek 官方搜索**：仅内置 DeepSeek V4.1 Flash 可直接选择；复用用户已保存的 DeepSeek Key，通过 `https://api.deepseek.com/anthropic/v1/messages`、模型 `deepseek-flash`、工具 `web_search_20250305` 获取结构化来源。
2. **OpenAI Responses 原生搜索**：用户提供 base URL、模型 ID 和 API Key；请求使用 `tools: [{"type":"web_search"}]`，读取结构化 source/citation 字段。
3. **Anthropic Messages 原生搜索**：用户提供 base URL、模型 ID 和 API Key；使用 `web_search_20250305` 并读取结构化搜索结果块。
4. **不使用联网搜索**。

除内置 DeepSeek 之外，不得因为聊天 Provider 写着“支持搜索”就自动开启；必须存在用户明确保存且测试通过的 Search Profile。允许用户明确选择“复用该 Provider 的 Key”，但仍要作为独立搜索配置保存并单独测试。

本版不实现无法定义响应格式的“任意 JSON 搜索 API”。README 必须准确说明只支持上述原生搜索协议，避免让用户误以为填入任意搜索网址都能工作。

### 4.3 SecretStore

- 将单一 DeepSeek Key 存储改为按 Provider UUID 隔离的 SecretStore。
- 每个凭据使用独立、稳定、不可逆派生的 Keystore alias；搜索凭据与聊天凭据分开。
- API Key 只保存为 Keystore 加密后的密文，不写入 SQLite、备份、日志、异常、截图、测试夹具、Gradle、Git 或 GitHub Actions。
- Provider 页面只能显示“未配置 / 已保存 / 已测试”，不能回显完整 Key。
- 替换 Key 使用事务式流程：新值完成加密、持久化、重新读取与常量时间比对后，再删除旧值。
- 删除 Provider 时先明确提示影响，再删除该 Profile 对应的 Key；不能删除其他 Provider 或健康数据。
- “无鉴权”只允许用户显式选择；HTTP 明文只允许 `localhost`、`127.0.0.1` 或模拟器宿主 `10.0.2.2`，其他地址必须 HTTPS。

## 5. 网络与协议架构

将当前写死的 `DeepSeekTransport` 重构为清晰分层：

- `ProviderProfileRepository`
- `ProviderSecretStore`
- `AiTransport` 接口
- `OpenAiChatCompletionsTransport`
- `OpenAiResponsesTransport`
- `AnthropicMessagesTransport`
- `AssistantRepository`
- `MultimodalDocumentRepository`（替代独立 Vision 模型概念）
- `SearchRepository`
- `DeepSeekNativeSearchClient`
- `OpenAiNativeSearchClient`
- `AnthropicNativeSearchClient`
- `ApiErrorMapper`
- `EndpointResolver`

### 5.1 URL 与 Endpoint 规则

- 用户输入的是 base URL，不要求输入完整业务 endpoint。
- 保存前规范化尾部 `/`，防止出现 `/v1/v1`、`//chat/completions` 或重复 `/messages`。
- 同时兼容常见 base URL 形态：域名根、带 `/v1`、已带厂商前缀。
- 若用户误填完整 endpoint，界面应识别并转换，或指出正确填写方式，不能静默拼接错误。
- 禁止 URL 中的用户名、密码、fragment；限制重定向，跨主机重定向不得携带认证头。
- 使用系统 TLS 校验，不提供“忽略证书”开关。
- 连接、读取、整体请求分别设置上限；请求可取消，页面销毁或新请求开始时旧回调不得覆盖新状态。

### 5.2 三种协议的请求与解析

每种协议分别实现文字、图片、系统提示、推理参数、非流式响应、错误响应和 usage 解析：

- OpenAI Chat Completions：`messages`；图片通过 `image_url` content block，可使用 data URL；读取 `choices[].message.content`。
- OpenAI Responses：`input` content blocks；图片使用 `input_image`；读取所有有效 `output` 项，不假设答案永远是第一个 block。
- Anthropic Messages：`messages` 与顶层 `system`；图片使用 `image` + base64 source；读取 `content` 中所有 text、thinking、tool result 与 citation block。

图片识别默认使用当前选择的同一个 Provider 和模型。只有用户配置的模型明确声明并通过图片能力测试时才允许发送图片。不要根据模型名字猜测能力。

文档识别继续执行“本地保存 → 明确确认上传 → AI 草稿 → 用户核对 → 正式保存”，失败不得删除原文件。压缩、大小限制、MIME 检测以真实文件内容为准，支持 JPEG、PNG、GIF 首帧和 WebP；PDF 保持本地逐页渲染后发送。

### 5.3 兼容性设置

自定义 Provider 的高级设置至少提供：

- 是否使用 developer role；否则降级为 system role。
- 最大输出字段使用 `max_tokens` 或 `max_completion_tokens`。
- 推理参数：不发送 / 标准 `reasoning_effort` / DeepSeek `thinking` + `reasoning_effort`。
- Anthropic 版本头。
- 认证头模式。
- 图片输入开关。

默认设置必须最小化，普通用户只需填写“名称、协议、base URL、模型 ID、Key”。高级项折叠显示。不要开放可随意覆盖 `Host`、`Authorization`、`Cookie` 等危险 Header 的自由输入框。

### 5.4 连接测试必须分层

Provider 的测试流程显示分步结果：

1. 本地配置校验。
2. DNS/TLS/网络连通。
3. 认证。
4. 最小文字请求。
5. 可选图片能力测试（由用户点击触发，使用内置匿名小图，不发送健康资料）。
6. 搜索能力单独测试，必须返回结构化 URL 来源才算通过。

`GET /models` 仅作为可选的“获取模型列表”便利功能，失败时允许手工填写模型，不能将不支持 `/models` 误判为聊天不可用。

错误至少区分：本地配置错误、401、402/余额、403、404/endpoint、模型不存在、请求字段不兼容、图片不支持、429、5xx、DNS、TLS、超时、响应过大、无效 JSON、空响应、搜索未返回结构化来源。错误信息不得包含 Key、认证头或原始健康内容。

## 7. 医疗上下文、隐私与提示词

- 自定义 Provider 不改变“最小必要上下文、发送前预览、用户确认”的原则。
- 每次请求必须显示即将发送的药物、过敏史、健康资料类别和图片数量；未选中的本地资料不得发送。
- 系统提示词移除“只允许使用旧 DeepSeek 模型”的硬编码，改为与 Provider 无关的医疗安全、来源分级、不确定性和就医边界。
- 系统提示词、官方本地资料、用户资料和联网搜索结果使用清晰分隔与不可信内容标记，防止说明书或网页中的提示注入覆盖系统规则。
- 回答继续按结论、核对事项、依据、来源、不确定性和就医提示展示。
- 自定义 API 可能由第三方运营；发送前明确提示数据将发往用户配置的域名。
- 备份与导出包含 Provider 非敏感配置时必须排除所有 API Key 和认证密文。

- 浅色、深色页面无默认紫色组件；API 输入页与今日、药物、资料、健康页面色调、按钮和间距一致。
- 360dp、412dp、默认/大字号、横竖屏恢复、键盘遮挡、TalkBack 标签、手势/三键导航。
- API 26 与 API 35 模拟器至少各完成一次核心流程；若环境缺失必须在报告中写明，不能伪造。

### 8.3 真实 API 测试边界

只有在运行时安全提供有效 Key 时才执行：

1. DeepSeek Key 保存与重启读取。
2. `deepseek-flash` 最小文字问答，记录服务实际返回的 model。
3. 使用匿名测试图片验证同一 `deepseek-flash` 多模态请求。
4. DeepSeek 官方搜索返回可点击结构化来源。
5. 至少一个用户选择的自定义 Provider 的文字请求；若没有其有效 Key，不标记通过。

测试 Key 只能通过应用界面或临时环境注入，测试后删除，禁止进入终端命令历史、源码、日志、报告、APK 字符串和 Git。没有 Key 时完成 Mock 测试即可，但验收报告必须把“真实 API”列为未验证。

## 9. 实施阶段、提交与防止死循环

按以下阶段执行，每阶段完成后形成独立提交：

1. `chore: prepare v0.4.0 provider migration`
   - 版本号、数据库 7、Profile 模型、迁移与 SecretStore。
2. `feat: add configurable ai protocol adapters`
   - 三种 Transport、URL 解析、错误映射与合约测试。
3. `feat: unify multimodal and configurable search`
   - `deepseek-flash` 图片能力、文档识别改造、三种搜索模式。
4. `feat: redesign ai provider settings`
   - 助手卡片、Provider/Search 设置页、统一 Design System 与深浅色。
5. `test: verify v0.4.0 provider workflows`
   - 单元、合约、迁移、UI/模拟器与回归测试。
6. `docs: publish v0.4.0 api support`
   - 中英文 README、截图、验收报告、Release 说明。

每个阶段最多两轮“集中修复 → 复测”。同一失败连续两次后停止重复构建，定位根因或在报告中记录唯一外部阻塞点。不得进行无限审查、无变化重跑或数小时轮询。一次完整测试通过后，不因非阻塞的格式偏好重复全量测试。
