# Luna Max 执行任务书：个人用药与健康助手 Android App

> 文档性质：产品需求总纲 + 分阶段连续执行任务书  
> 执行方式：先完成系统调研和候选验证，再自动编写详细开发计划，最后开发、轻量验证并交付  
> 主要执行者：Luna Max  
> 编写日期：2026-09-19  
> 首发平台：Android  
> 主要适用地区：暂按中国大陆规划，调研后确认  

## 1. Luna Max 必须先理解的任务边界

用户最终想要的是一款个人使用的 Android 用药与健康助手。它既要可靠地提醒吃药，也要管理家中已有药品、识别药盒和说明书、提醒药物过期，并在回答健康问题时安全地参考用户的个人健康档案。

整个任务采用同一会话分阶段连续执行。Luna Max 必须先完成第一阶段调研，保存并自检全部调研产物，然后才能进入详细开发计划和正式开发。第一阶段必须：

1. 完整阅读本任务书。
2. 重点搜索和验证 GitHub 上相关开源项目。
3. 调研可合法使用的权威药品资料来源与药物相互作用数据来源。
4. 调研 Android 提醒、离线存储、OCR、药品说明书本地检索和 DeepSeek API 接入方案。
5. 对高价值候选项目进行实际下载、构建或最小验证，不能只看 README。
6. 将所有结论、证据、链接、许可证、验证过程和推荐方案保存为独立调研文档。
7. 第一阶段内不要开始正式产品代码开发，不要凭调研阶段的临时代码建立最终架构；第一阶段自检完成后按本任务书自动进入第二阶段。

第一阶段允许为了验证候选项目而进行临时构建、运行测试或小型概念验证，但必须与未来正式项目目录隔离，并在调研文档中说明。

## 2. 最终产品目标

产品需要解决以下核心问题：

1. 用户设置好药物和服用计划后，App 自动按时提醒。
2. 用户服药后可点击勾选，系统保存实际服用时间和状态。
3. 用户可以同时管理多种正在服用的药物，包括鼻炎药、处方药、非处方药和临时用药。
4. 用户可拍摄药盒、药瓶和随药附带的纸质说明书，由系统识别并生成药物记录。
5. 用户可管理已经购买但当前不吃的药物，并按有效期、开封期和库存状态获得提醒。
6. 系统结合权威药品资料，检查多药同服、成分重复、过敏、疾病禁忌等风险。
7. 系统建立个人健康档案，让 AI 在回答健康问题时按需参考既往病史、过敏史、历史用药、检查报告和不良反应。
8. AI 不应每次机械复述用户的完整病史，但相关病史影响答案时必须体现，并允许用户查看本次回答参考了哪些个人资料。
9. 系统必须区分“规则或权威资料给出的结论”和“AI 对资料的解释”，不能让大语言模型独自决定药物是否能一起服用。

产品定位是辅助记录、提醒、资料整理与风险提示，不是医生替代品，不得擅自指导用户停用处方药、改变处方剂量或延误紧急就医。

## 3. 核心功能范围

### 3.1 今日用药

首页展示当天需要完成的用药任务。每条任务至少包含：

- 药物通用名和商品名
- 药物图片
- 单次剂量及单位
- 计划时间
- 饭前、饭后、随餐、空腹或其他要求
- 简短备注
- 已服用
- 稍后提醒
- 跳过
- 未服用或忘记服用

服药记录必须保存计划时间、实际操作时间、最终状态和用户备注。

计划类型至少考虑：

- 每日一次或多次
- 每隔若干小时
- 每周指定日期
- 连续服用若干天
- 固定疗程
- 临时用药
- 按需服用
- 暂停后恢复
- 当天单次调整
- 跨时区后的时间确认

提醒系统必须调研 Android 后台限制、通知权限、精确定时、设备重启、厂商省电策略和时区变化。

### 3.2 正在服用的药物

每种药物至少能够记录：

- 通用名
- 商品名
- 有效成分
- 剂型
- 规格
- 批准文号或其他可识别编号
- 生产厂家
- 单次剂量
- 服用频率
- 用药原因
- 开始和结束日期
- 开药医生或医疗机构
- 药盒照片
- 药片或药瓶照片
- 随药说明书照片或扫描页
- 用户备注
- 信息来源和最后更新时间
- 实际服用历史

### 3.3 家庭药箱

用于保存当前没有服用、但用户已经拥有的药物。每一个实际药盒或药瓶应作为独立库存批次，避免把同一种药的不同有效期混在一起。

至少记录：

- 标准药品信息引用
- 数量和数量单位
- 批号
- 生产日期
- 有效期
- 开封日期
- 开封后使用期限
- 存放位置
- 储存条件
- 包装和说明书照片
- 当前状态
- 丢弃日期和丢弃原因

状态至少包括：

- 正在服用
- 库存中
- 已暂停
- 已停用
- 已用完
- 即将过期
- 已过期
- 已丢弃

计划中的到期提醒节点包括 90 天、30 天、7 天和到期日，最终应允许用户自定义。

### 3.4 药品拍照与自动录入

建议引导用户依次拍摄：

1. 药盒正面。
2. 药盒侧面或背面。
3. 条形码、追溯码或批准文号。
4. 生产日期、批号和有效期区域。
5. 随药附带的完整纸质说明书。

系统尝试识别：

- 商品名和通用名
- 有效成分
- 规格和剂型
- 批准文号
- 生产厂家
- 生产日期、有效期和批号
- 用法用量
- 禁忌、不良反应和注意事项
- 药物相互作用
- 特殊人群说明
- 储存条件

所有自动识别结果必须经过用户确认才能写入正式记录。低置信度字段要单独标记，尤其是剂量、有效期、成分和禁忌信息。

### 3.5 随药说明书本地资料库

这是正式需求，不是普通附件功能。

用户上传药品时，可以同步拍摄或导入该药自带的说明书。说明书原图、OCR 文本、结构化章节和来源关系均保存在手机本地。建议的数据结构包括：

- 原始照片或 PDF
- 页码和拍摄顺序
- OCR 原文
- OCR 置信度
- 用户修正后的文本
- 结构化章节，如成分、适应症、用法用量、不良反应、禁忌、注意事项、相互作用、特殊人群、储存、有效期
- 对应的药物和实际药盒批次
- 生产厂家、说明书版本或修订日期（如可识别）
- 创建时间和最后修改时间
- 内容指纹，用于避免重复导入

本地说明书应被视为重要的一手资料，但系统必须清楚标注它是“用户拍摄的随药说明书”，不能在未验证时把它等同于当前最新版在线说明书。纸质说明书可能较旧、拍摄不完整或 OCR 有误。

### 3.6 本地资料、个人档案与联网资料的联合检索

AI 回答健康或药品问题时，要建立一个小型、可追踪的资料检索框架。资料来源分层如下：

1. 用户当前药物和实际服药记录。
2. 用户拍摄并确认的本地药品说明书。
3. 用户健康档案和历史医疗资料。
4. 已同步或缓存的权威药品结构化数据。
5. 实时联网检索到的监管机构、官方说明书、专业指南或可信医学资料。

推荐的回答流程：

1. 识别用户问题涉及的人、药物、症状和时间范围。
2. 从本地数据库筛选相关药物、病史、过敏史和服药记录。
3. 从本地说明书索引检索相关章节，而不是把所有文件全部发送给模型。
4. 在需要最新资料、存在冲突或本地信息不足时发起联网检索。
5. 对不同来源进行版本、地区、厂家、规格和更新时间比较。
6. 先由确定性规则或结构化数据完成药物风险检测。
7. 再由 DeepSeek 将检索结果和规则结果解释成易懂的答案。
8. 在答案中显示关键来源，提供“本次参考资料”入口。
9. 如果信息不足或来源冲突，明确说明不确定性，不得自行补全。

需要为每一条送入模型的资料保留来源标识，最终能够追踪某个结论来自：

- 哪一盒药的哪一页说明书
- 哪条个人健康记录
- 哪个官方网页或数据库记录
- 哪条药物相互作用规则
- 资料的日期、版本和适用地区

#### 3.6.1 “权威资料”的定义与证据等级

本产品中的“权威”不是指网页排名靠前、写得像医学文章或被 AI 多次引用，而是指来源身份可验证、责任主体明确、内容可追溯、版本和适用范围可确认的资料。建议按以下等级处理：

**A 级：监管与正式原始资料，优先级最高**

- 国家或地区药品监管机构发布的药品批准信息、安全警示、召回信息和正式说明书。
- 与用户手中具体厂家、规格、剂型相匹配的随药纸质说明书或厂家正式电子说明书。
- 国家卫生主管部门、国家级公共卫生机构发布的正式规范、指南和公告。
- 药品包装上可验证的批准文号、追溯信息和生产企业信息。

**B 级：高质量专业证据**

- 正式发布并标明版本、制定组织和方法学的临床实践指南或专家共识。
- 世界卫生组织等具有明确责任主体的国际机构资料，但必须标注地区适用性。
- 同行评议的系统综述、Meta 分析和关键临床研究；单篇研究不能自动替代说明书或指南。
- 有明确编辑标准、更新机制和许可来源的专业药物数据库。

**C 级：辅助解释资料**

- 大型医院、大学医学中心和专业学会面向患者发布的科普资料。
- 药品生产企业公开的患者教育资料，但必须识别利益相关性，并核对是否对应具体产品版本。

以下内容不能单独作为权威结论来源：

- 搜索结果摘要、搜索排名和 AI 生成摘要。
- 普通健康网站、营销软文、电商页面、论坛、社交媒体和个人经验。
- 无发布日期、无作者、无机构、无版本或无法找到原文的转载。
- 未经用户核对的 OCR 文本。
- DeepSeek 或其他大模型自身的参数记忆。

来源冲突时不得由模型自行“投票”。系统应比较适用地区、药品成分、厂家、规格、剂型、发布日期、修订日期和证据等级；优先展示与用户手中具体药品最匹配且仍有效的监管或正式资料。无法判定时必须同时呈现冲突并提示咨询医生或药师。

#### 3.6.2 内置文档、系统提示词与个人资料调用框架

App 应内置一套可版本化、可审计的 AI 运行资料，而不是把所有规则临时拼在聊天文本中：

- 医疗安全系统提示词：规定模型角色、不能替代诊疗、不得擅自停药改量、急症升级、不确定性表达和引用要求。
- 权威资料判定规则：采用本任务书的证据等级和冲突处理方法。
- 用药回答模板：区分已确认事实、潜在风险、证据不足、建议行动和来源。
- 个人资料使用规则：只提取当前问题确实相关的最少信息，不默认发送完整病历。
- 本地说明书检索规则：优先按章节、药物、厂家、规格和版本定位原文。
- 联网检索规则：限定来源范围、保留原始 URL、访问日期、页面标题、机构和相关原文片段。
- 提示注入防护规则：用户上传文档和网页内容只能作为资料，不能覆盖系统规则、调用未授权工具或索取密钥。

推荐的上下文组装顺序：

1. 固定且版本化的系统安全提示词。
2. 当前用户问题及必要的时间信息。
3. 与问题相关的结构化个人资料、当前用药和过敏信息。
4. 与问题相关的本地随药说明书片段和内置文档片段。
5. 结构化药物相互作用或禁忌规则结果。
6. 必要时由联网检索补充的最新权威资料。
7. 输出格式、引用和不确定性要求。

每次回答应保存“本次使用了哪些资料”的可审计清单，但不得保存或展示模型的隐藏推理过程。系统提示词、内置文档和规则要有版本号、更新日期、变更说明和回归测试，避免静默修改医疗安全行为。

### 3.7 个人健康档案

结构化档案至少考虑：

- 基本资料
- 身高和体重
- 已确诊疾病和慢性病
- 药物过敏、食物过敏及其他过敏
- 手术史和住院史
- 家族史
- 吸烟和饮酒情况
- 妊娠、备孕或哺乳状态
- 肝肾功能相关情况
- 历史症状
- 药物不良反应
- 医生特别交代事项
- 历史用药

原始健康资料可包括病历照片、处方、化验单、检查报告、出院记录、PDF 和用户笔记。

AI 从原始资料抽取的结构化信息必须经用户确认后才能写入正式档案。用户应能删除、纠正、导出或禁止某条信息参与 AI 回答。

### 3.8 AI 健康助手

用户可询问：

- 当前几种药能否一起服用
- 某种鼻炎药能否加入当前用药
- 是否存在重复成分
- 漏服后应查阅哪些说明或联系谁
- 某种症状是否可能与近期用药有关
- 既往是否出现过类似不良反应
- 某份检查结果中有哪些值得关注的信息

AI 默认不机械复述完整病史，只在确实相关时使用。若病史对答案产生关键影响，必须说明相关因素，并提供“本次使用了哪些个人资料”的透明入口。

## 4. 用药安全分析原则

药物安全分析不能采用“只把药名发给大模型，让模型自行判断”的方式。目标架构必须至少分为：

1. 名称标准化层：商品名、通用名、成分、规格和剂型归一化。
2. 结构化规则层：相互作用、重复成分、禁忌、过敏和特殊人群规则。
3. 个人资料检索层：按问题检索必要的健康档案和历史记录。
4. 本地说明书检索层：定位随药说明书的相关章节。
5. 联网证据层：补充最新官方资料和专业来源。
6. AI 解释层：组织、总结和解释已有证据，不自行制造证据。

至少调研以下风险类别：

- 药物与药物相互作用
- 相同有效成分重复
- 同类药物重复
- 药物与疾病冲突
- 药物与过敏史冲突
- 药物与食物、酒精或保健品的相互作用
- 肝肾功能相关风险
- 年龄相关风险
- 妊娠和哺乳相关风险
- 剂量或服用间隔异常
- 饭前、饭后等服用条件冲突

高风险情况只能提供风险提示、证据和就医或咨询药师建议，不能替代处方决定。

## 5. DeepSeek API 已核验的当前配置

以下内容已于 2026-09-19 根据 DeepSeek 官方 API 文档核验。Luna Max 在正式开发前仍必须再次访问官方文档确认，因为模型名称、版本、参数和价格会变化。

### 5.1 当前官方基础地址与唯一模型

- OpenAI 兼容 API Base URL：`https://api.deepseek.com`
- App 唯一使用的模型 ID：`deepseek-flash`
- 截至核验日，`deepseek-flash` 对应 DeepSeek-V4.1-Flash。
- 不应再把已退役的 `deepseek-chat` 或 `deepseek-reasoner` 作为新项目默认模型。

确定的产品策略：

- 所有 AI 功能统一使用 `deepseek-flash`，包括健康问答、复杂资料综合、风险解释、OCR 后处理和图像辅助识别。
- 项目不接入、不配置、不展示其他 DeepSeek 模型，也不建立自动切换到其他模型的逻辑。
- Base URL 和 `deepseek-flash` 模型 ID 通过集中配置管理，禁止在多个业务模块中重复硬编码。
- 药品说明书的 OCR 和关键字段识别不应只依赖云端视觉模型；需要比较本地 OCR、DeepSeek 视觉能力和混合方案。

### 5.2 用户可调思考深度

App 设置中提供以下四档，不直接向普通用户展示难懂的内部参数：

| App 显示 | API effort | 适用场景 |
|---|---|---|
| 快速，不深度思考 | `none` | 简单查找、界面说明、低风险整理 |
| 较低 | `low` | 简单资料归纳 |
| 标准 | `high` | 默认健康问答和日常综合分析 |
| 最高 | `max` | 复杂病史、长说明书、多药证据综合 |

官方当前说明：思考模式默认开启，默认 effort 为 `high`。OpenAI Responses API 格式可使用 `reasoning.effort = none / low / high / max`；Chat Completions 兼容格式的控制方式不同，需要按官方文档实现和验证。

需要在调研报告中确认：

- Android 或后端最终采用 Responses API 还是 Chat Completions。
- 流式输出事件的正确处理方式。
- 开启工具调用时，推理内容的上下文回传要求。
- thinking 模式下哪些参数无效。
- `max_output_tokens` 如何同时控制推理和最终回答长度。
- 不同 effort 的速度、成本和回答质量差异。

### 5.3 内置配置与密钥安全

App 可以内置经过核验的 Base URL、唯一模型 ID `deepseek-flash` 和支持的 effort 档位，但绝对不能把真实 DeepSeek API Key 硬编码到 APK、Git 仓库或客户端日志中。

调研必须比较两种方案：

1. 用户自己填写 API Key，使用 Android Keystore 加密保存，并由 App 直接访问 DeepSeek。
2. App 通过自有后端代理访问 DeepSeek，密钥只保存在服务端。

必须从个人使用成本、隐私、部署难度、密钥泄露、限流、审计和未来公开上架等角度给出建议。若未来公开发布，原则上优先采用安全后端代理或用户自带密钥方案。

### 5.4 测试 API Key 的临时使用与清除

用户可以为集成测试临时提供 DeepSeek API Key，但真实密钥不得进入任务书、聊天提示词、源代码、Git 历史、Gradle 配置、APK/AAB、测试报告、截图、终端输出或构建日志。

测试时必须遵守：

- 仅通过进程级临时环境变量、系统安全密钥存储或运行时人工输入使用。
- 不把密钥写入 `.env` 后提交；确需临时文件时必须位于 Git 忽略且权限受限的隔离目录，并在测试后安全删除。
- HTTP 日志、崩溃日志和调试输出必须对 `Authorization` 等敏感字段脱敏。
- 只用虚构健康数据测试，不把真实病历或完整个人档案发送给测试接口。
- 测试结束后清除环境变量、临时配置、Harness Home 中可能保存的凭据和相关进程。
- 对源代码、资源、构建缓存、测试产物、APK/AAB 解包内容和 Git 历史执行密钥残留扫描。
- 最终交付包只能保留“用户运行时输入自己的 Key”或安全后端代理能力，不得包含任何测试 Key。
- 由于任何通过聊天发送的真实密钥都应视为可能暴露，完成验证后应撤销该 Key 并重新生成。

### 6.1 UI/UX 与视觉质量要求

- 在实现正式界面前先提供至少 2 至 3 个视觉方向或关键页面方案供用户选择。

Figma 插件已于 2026-09-19 安装并连接。后续 UI 阶段应通过 Figma 完成可编辑界面、设计系统、关键交互状态和视觉评审，再交给 Codex 或开发代理实现。插件不能代替产品判断；生成结果仍要进行人工审美、可用性和无障碍检查。

## 7. 后续正式开发的暂定技术方向

本节只是调研假设，不是已经确定的选型。Luna Max 应通过调研验证或提出更可靠方案。

### 9.7.1 DeepSeek Harness 联网检索流程

联网检索的确定方案是直接采用 DeepSeek 官方开源项目 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) 中现有的 Web Search、Web Fetch、Agent 工具调用和来源整理能力。产品不得要求用户申请 Bing、Google、Serper 或其他第三方搜索 API Key；联网搜索只使用 DeepSeek Harness 官方搜索链路和 DeepSeek token 消耗模式。

Luna Max 必须对官方仓库实际源码完成验证，以定位并集成官方搜索组件及其必要依赖。技术实现优先直接复用官方包；如果 Android 运行环境无法原样承载其 Node、Python 或原生依赖，则应在受控后端运行官方搜索组件，或移植使其可在目标环境工作的最小必要代码，但不得换成第三方搜索服务，也不得只做一个外观相似的模拟搜索。重点研究：

- 官方仓库中真正负责查询、打开网页、提取正文、重复结果合并和来源记录的包、插件和调用链。
- 搜索结果由什么服务或端点提供，是否真的不需要第三方搜索 API Key，以及实际成本是否仅体现为 DeepSeek token 和普通网络流量。
- 搜索、抓取和模型工具调用分别消耗什么资源，失败、限流、验证码和不可访问页面如何处理。
- 能否只允许访问白名单或高可信域名，并按本任务书的证据等级筛选。
- 如何防御网页提示注入、恶意下载、重定向、追踪脚本和不可信证书。
- 如何保存原始 URL、页面标题、发布机构、发布日期、访问日期和支持结论的片段。
- 官方 Harness 当前为开发者预览且快速变化，是否适合直接嵌入生产 App；必须核对安全声明、MIT 许可证、第三方 notices、版本锁定和升级风险。
- Harness 运行环境、Node/Python/原生依赖是否适合 Android；若不适合，后端隔离运行或有限逻辑移植的成本与安全边界。

最终实现必须做到：Harness 或其检索流程只负责发现和取得候选资料，不能因为“由官方 Harness 搜到”就自动把网页判定为权威；来源仍需经过机构身份、版本、地区、药品匹配和证据等级校验。

## 11. 调研报告质量标准

所有重要结论必须满足：

- 有可访问的原始链接。
- 标注访问或核验日期。
- 明确区分官方事实、实际测试结果和推测。
- 不用 star 数量代替技术判断。
- 不把 README 宣称当成已验证事实。
- 不忽略许可证和数据授权。
- 不用 AI 自身记忆替代最新官方文档。
- 对无法确认的内容明确写“未确认”。
- 对失败的构建或验证保留原因，而不是隐藏。
- 对安全和医疗风险采用保守结论。

GitHub 项目最终建议应使用统一评分表，至少包括：功能匹配、代码质量、可构建性、维护状态、许可证、安全、隐私、可扩展性、中文适配和改造成本。

## 12. 未来开发阶段的大致顺序

第一阶段调研结束并完成自检后，由同一个 Luna Max 会话直接读取全部调研报告，编写 `../plans/08_详细开发执行计划.md`；计划自检通过后继续正式开发。无需等待外部代理做重复研究或形式化审阅。阶段如下：

### 阶段 A：可靠的离线用药基础

- 手动添加药物
- 服药计划
- 系统提醒
- 已服用、延后、跳过和漏服
- 用药历史
- 家庭药箱
- 有效期提醒
- 基础健康档案

### 阶段 B：拍照录入和说明书资料库

- 药盒拍照
- 条形码或批准文号识别
- OCR
- 有效期识别
- 说明书多页拍摄
- 本地说明书结构化、检索和引用
- 用户确认与纠错

### 阶段 C：用药安全检查

- 药名和成分标准化
- 重复成分检测
- 相互作用规则
- 过敏和疾病冲突
- 风险等级
- 来源展示

### 阶段 D：DeepSeek 个人健康助手

- DeepSeek 安全接入
- 用户可调思考深度
- 本地说明书检索
- 个人健康档案检索
- 权威联网资料检索
- 证据融合和冲突处理
- 回答引用和资料使用透明度

### 阶段 E：完整验证与交付

- 核心单元测试、集成测试和短时冒烟测试
- 当前可用模拟器或设备上的关键流程验证；不强求穷举所有 Android 版本
- 使用可控时钟、状态注入和自动化方式验证提醒，不进行 30 分钟或数小时的真实等待测试
- 使用少量有代表性的 OCR 样例验证关键字段
- 对高风险 AI 场景做精简安全检查
- 对密钥、敏感日志和最终构建包做一次重点安全扫描
- 检查实际采用依赖的许可证，不对未采用候选重复审查
- 对核心页面做一次无障碍和视觉一致性检查
- 构建可安装 APK；具备条件时再构建 AAB 或正式签名包
- 用户使用说明、构建说明、已知限制和风险提示

### 阶段 E 的时间盒与防循环规则

本项目是个人应用原型和可用版本，不采用重型审计流程。验证的目标是发现会影响安全和主要功能的问题，而不是无限追求零警告或形式完美。

- 每个开发阶段最多进行 2 轮“检查—修复—复测”。第二轮仍存在的非阻断问题写入已知限制，不继续循环。
- 同一个失败原因连续出现 2 次时停止重复尝试，保存日志、原因和建议处理方法，然后继续其他可完成工作。
- 全量构建和全量测试最多各进行 1 次；出现修复时只重跑受影响测试，最后再做 1 次核心冒烟，不重复整套审查。
- 不进行 30 分钟、数小时或通宵的真实等待、稳定性或定时提醒测试。使用测试时钟、依赖注入、缩短后的触发时间和状态模拟。
- 单个没有新输出的命令超过合理时间应终止并诊断一次，不因“可能再等等”反复延长。
- 网络调用最多重试 3 次，并使用退避；仍失败则记录网络、服务或密钥条件，不继续消耗 token 重试。
- UI 最多完成一轮集中视觉调整和一轮必要修正；不因非关键像素差异反复重做 Figma 和代码。
- 静态分析、安全扫描和许可证扫描各执行 1 次；仅对高危或阻断问题修复后复扫相关部分。
- 外部条件缺失，如 API Key、签名证书、真机或付费数据源，不得卡住整个任务；标注为待用户验证并继续交付。
- 优先保证可安装、可打开、提醒与记录主流程可用、数据不泄露。低优先级优化进入待办清单。
- 最终报告应简洁说明“已验证、未验证、已知限制”，不得为了扩大报告而重复执行已经通过的步骤。

具体模块拆分、代码审查节点、精简验证矩阵、打包方式和验收标准，由 Luna Max 在完成第一阶段调研后写入 `../plans/08_详细开发执行计划.md`。计划必须遵守本任务书的防循环规则，完成一次一致性自检后直接执行，不等待外部代理再次评审。

## 13. 明确不允许的捷径
